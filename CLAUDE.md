# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Fineva is a Flutter app (Android + Windows, Linux for development) for keeping the financial records of private persons and Hungarian sole proprietors (egyéni vállalkozók); being usable for sole proprietors is the goal. UI languages are English and Hungarian. It is written from scratch, with the architecture of the author's calibre_touch app. It must not contain code copied from other apps: ~/vscode/monekin (a runnable Flutter project) holds the AGPL-3.0 Monekin sources the project was first started from, for ideas only.

## Commands

```bash
flutter pub get        # also regenerates l10n (pubspec has generate: true)
flutter analyze
flutter test
flutter test test/datasource_test.dart
flutter run -d linux   # or windows / an Android device id
```

`flutter test` loads the system's libsqlite3 (`test/test_database.dart`), because the sqlite bundled by sqlite3_flutter_libs only exists in a built app.

Test data for every kind of user, in the app and in the workbooks of `assets/` (see `tool/test_data/README.md`):

```bash
python3 tool/test_data/build_test_data.py   # test_data.json + fills the workbooks
FINEVA_DB=~/.local/share/com.example.fineva/fineva.db flutter test tool/seed_test_data.dart   # replaces every user!
```

## Architecture

Data flows through these layers: **Riverpod providers → `FinanceNotifier` → `FinanceRepository` → `FinanceDatasource` (sqlite)**. Folders export through barrel files (`utils.dart`, `providers.dart`, `pages.dart`, `widgets.dart`, `config.dart`, `data_export.dart`); import the barrel rather than single files.

- `lib/main.dart` loads SharedPreferences and starts `ProviderScope`; `lib/app/app.dart` builds `MaterialApp.router` from `localeProvider`, `modeProvider` and `routesProvider`.
- `lib/config/`: go_router routes (`Routes` enum in `utils/enums.dart`, each page has a static `builder`) and the light / dark theme (both from `_theme`, only the brightness differs). The menu's pages (`MainDestination` in `widgets/main_navigation.dart`: dashboard, entries, business (a sole proprietor), statistics, accounts, categories, settings; an invoices only user's are different, see below; `MainDestination.visible`) are in a `ShellRoute` and switched with `go`. The other pages (entry, transfer, invoice, an account `/accounts/:id`, profile, rates) are in the `ShellRoute` too, pushed over the menu's pages (an account is a child route of the accounts), so on wider screens the menu stays beside them; `MainDestination.at` maps them to their menu item (an account to the accounts, profile / rates to the settings). On a phone they have the back button (`backButton`) and the drawer opens by swiping from the edge (`mainDrawer`). Only the splash and the onboarding are outside the shell.
- `lib/data/datasource/finance_datasource.dart`: the app's own database, `fineva.db` in the app support folder, opened through the sqflite_common_ffi factory with the sqlite of sqlite3_flutter_libs. Generic, table-parameterized functions (`getAll`, `getById`, `insert`, `update`, `delete`) work with every model through `DbModel` (`id` + `toMap`, and each model has `fromMap` and a `table` constant). Only queries a single model can't express (balances, counts) are written out. Prefer extending the generic functions over adding one function per table.
- Schema: `schemaVersion` + `_upgradeSchema` (sqflite's version/onUpgrade). `_createSchema` makes the version 1 tables, then runs every upgrade step, so a new database is exactly an upgraded one: changing the schema means raising `schemaVersion` and adding a step (`_v2`, `_v3`, ...), never editing an old step. Foreign keys are on, so a table can't be rebuilt in a step (dropping it would cascade); add nullable columns instead. Deleting a user deletes their accounts (and so entries) and categories; an account can only be deleted without entries (`FinanceNotifier.deleteAccount` refuses, the account dialog disables it; the cascade to its entries is only for deleting a user); deleting a category leaves its entries without category.
- `lib/data/repositories/`: `FinanceRepository` (save = insert without id, update with id). Accounts, categories and entries are read by user id.
- `lib/providers/finance/`: `FinanceNotifier` loads the users, and the current user's accounts, categories, entries and balances into `FinanceState`, and reloads everything after each write (write methods return true on success). It sets the current user's id on saved accounts and categories. `FinanceState` has the lookups and totals the pages need; `Statistics` (`statistics.dart`) computes the statistics page's figures from it.
- Settings (language, theme, current user, onboarding at every start) are in SharedPreferences through `SharedUtility`; the language defaults to the device language if it's en or hu.
- **Start:** every platform starts at `SplashPage`. Once the data is loaded it goes to `OnboardingPage` if there is no user yet or Settings → "Onboarding at every start" is on (`onboardingAtStartProvider`, on by default for now), otherwise `DashboardPage`. Windows and Linux show it for at least `SplashPage.minDuration`; Android keeps the native splash (flutter_native_splash, `preserve` in main.dart, same look) until `FinanceState.loaded`, at most `Fineva.maxSplashDuration` (app.dart), so there it goes on at once.
- **Responsive layout** (`widgets/responsive.dart`, `widgets/main_navigation.dart`; the idea is Monekin's, the code is our own): `ScreenSize` compact (< 720: the menu is a drawer, `mainDrawer`), medium (a `NavigationRail`), expanded (>= 1140: the `MainMenu` always open). `MainShell` puts the menu beside the page; on a phone back on a menu page other than the dashboard goes to the dashboard. `ResponsiveRow` puts cards side by side from medium width.
- **Periods** (`DatePeriod`, `providers/finance/date_period.dart`; the idea is Monekin's date ranges): a week (Monday to Sunday), a calendar month, quarter or year, any days (custom), or all time, with the period before / after (`hasNext` is false when the next one is wholly in the future). `DatePeriod.range` makes a whole week / month / quarter / year that kind. `PeriodBar` (`widgets/period_picker.dart`): ‹ name ▾ ›, the name opens `showPeriodPicker` (the kinds as tiles; custom opens the date range picker); `periodName` gives the shown name. `dense` is the narrow form for an app bar's actions (short name, narrow arrows, the name at most 140 wide on a phone, so the title still fits at 360). The dashboard and the statistics share one period (`periodProvider`, this month at start, kept while the app runs).
- **Dashboard** (`DashboardPage`): the start page (no greeting: the user's name is in the menu's header). For the period chosen on the right of the app bar (`PeriodBar` dense) it shows the balances at its last day (now for all time; `FinanceState.balancesAt`; the total in the main currency, each account in its own with ≈ the main), the income / expenses in the main currency (`FinanceState.periodTotals`) and the latest entries; its "All" button opens `EntriesPage` filtered to that period (`/entries?from=2026-11-01&to=2026-11-30`, `EntriesPage.location`). For a sole proprietor it also shows the open (unpaid) invoices: receivables and payables per currency.
- **Entries** (`EntriesPage`): every entry; in the app bar the search (note, category, account, amount; case and accents ignored, every word must match) and the filters (a bottom sheet: type, account, category or none, period with the period picker; the badge counts them); the filters set are removable chips above the list, with the count and totals of what is shown; the order (`EntrySortButton`: the newest / oldest first, the largest / smallest amount first, with its sign (an expense is less than any income), in the main currency; a dot on the button when not the newest first; `EntryFilter.sort`, not counted as a filter, kept when the filters are cleared). The logic is `EntryFilter` (`providers/finance/entry_filter.dart`). Dashboard and entries use `FinanceContent` for the loading / error / no account states.
- **Entries open to be looked at** (safer): tapping an entry in a list (dashboard, entries, an account) opens `EntryPage` as `EntryView` (with the account's balance just after it, `FinanceState.balanceAfter`, from the saved entries, so it follows a change; a transfer's view has both sides'; its button below closes it); the app bar's edit button switches to the form, whose back / close goes back to looking at it (also after saving). The edit button at the end of each `EntryTile` (`onEdit`) opens it right to editing (`openEntry(edit: true)`, route parameter `?edit=1`, `editEntryParameter`); then back goes back to the list. An entry booking an invoice's payment is looked at like the others, and edited on its invoice.
- **Accounts** (`AccountsPage`, `AccountPage`): tapping an account opens its page (long press edits it): the balance now (≈ the main currency), then its entries like a bank statement, by day, the newest first, each day with the balance at its end (`FinanceState.ledger`), the opening entry among them (without one, a button below gives it: `openNewOpening`, route parameter `?opening=1`); for recording and checking entries. Its app bar has the entries page's search and filters (`EntrySearchField`, `showEntryFilterSheet` without the account, `ActiveEntryFilters`; `widgets/entry_filters.dart`): filtered, it shows the entries found with their dates and totals, without the balances (they wouldn't add up), and that list can be sorted (the statement can't). Its + button adds an entry on that account (`AddEntryButton(account:)`, `EntryPage` takes an [Account] as `extra`); the account itself (seldom) is edited from the balance card.
- **Account details and closing** (since schema 14): an account's optional description, account number (`bankAccount`: a Hungarian GIRO number or an IBAN, check digits checked, `parseBankAccount` in `utils/bank_ids.dart`; not for cash) and SWIFT / BIC (`parseSwift`), shown on its page. It can be closed (`Account.closedDate`; the account dialog's switch and day) only with a 0 balance on that day and no entries after it (`FinanceState.closingCheck`; `FinanceNotifier.saveAccount` refuses otherwise): its entries stay (searchable, editable), it is listed apart under "Closed accounts", and left out where new entries go (`FinanceState.openAccounts(keep:)` in the entry, transfer and invoice forms; no + on its page; an entry's day can't be after the closing). The balance card leaves out a closed account with 0 balance. It can be reopened. Deleting stays only for an account without entries.
- **Statistics** (`StatisticsPage`, charts in `widgets/stats_charts.dart` with fl_chart): the shared period (dense `PeriodBar` in the app bar; the title shrinks to fit on a narrow phone), in the main currency (`Statistics`: entries at the rate of their day, balances at the rate of each day; amounts without a rate are left out and noted by `MissingRatesNote`): summary tiles (income, expenses, difference each compared with the period before of the same length, `Statistics.previous`, `PeriodComparison`: the change in percent, green the good way, red the other, and the value then; also on the dashboard's period card), categories (ranked bars and a thin segmented bar, not a pie), the balance line (a point a day, a month for all time or over 400 days: `Statistics.monthlyBalance`), cash flow bars with a table (`Statistics.cashFlowStep`: by day up to a week, 7 days up to two months, month up to two years, otherwise year).
- **Users** (`Profile`, table `profiles`, since schema 4; before that one `profile` row): every user has their own accounts and categories (`user_id`), and so entries; a new user gets the built-in categories of their kind (`FinanceDatasource.insertProfile`, `BuiltInCategories.forNewUser`). A user's kind (personal / sole proprietor) is fixed once saved: `UserTypeChoice` only lets a new user choose. A user is: name, address, tax identification number (adóazonosító jel) and, for a sole proprietor, tax number (adószám); personal or sole proprietor finances, and for a sole proprietor the taxation (`TaxRegime`: itemized "sima" SZJA, flat-rate átalányadó, KATA), `VatStatus` (exempt / registered) and EU reporting (összesítő nyilatkozat), which needs the EU VAT number (közösségi adószám, since schema 5). No user = the first onboarding isn't finished. The onboarding (language and which user, user type, details, then the business step only for a sole proprietor; an existing user can skip; its pages only change with the buttons, so the details and the business step are validated) saves the user and makes it current. Users are switched in the menu's header (the rail's avatar): `UserSwitchButton` (`widgets/main_navigation.dart`), a dropdown of the users that asks before switching, then goes to the dashboard; its last item, "New user", opens `ProfilePage` with a new `Profile` (kind, details, taxation; saved, it is the current user, and their dashboard opens). There is no managing the users (the user isn't an admin: really one person keeping their records one way or another). `ProfilePage` (Settings) edits the current user (not their kind, which isn't shown: fixed), deletes them (not the last). The onboarding at every start is only for testing and will go; the first one (no user yet) stays. They use `UserTypeChoice`, `UserDataForm` and `BusinessProfileForm` (`widgets/profile_form.dart`). The business fields and the tax number are kept for a personal profile too.
- **Sole proprietor records** (`BusinessPage`, menu item only for a sole proprietor; `InvoicePage`): `Invoice` (table `invoices`, since schema 6): outgoing (revenue) or incoming (cost), partner in Hungary / the EU / a third country, one `VatCode` per record (rates, NAV Online Számla case codes AAM, TAM, ATK, FAD, KBAET, EUFAD37, EUFADE, EUE, EAM, HO, NAM, and the reverse charged purchases; `VatCode.available` filters them by direction and location), amounts in the invoice's currency with an exchange rate (`Invoice.rateScale`, of `Invoice.rateDate`: the fulfillment, or the issue if earlier; the revenue and the VAT count at it whenever it is paid), and its payments (see below). The calculations are pure classes in `lib/providers/business/`, after the user's workbooks in `assets/_Bevételi nyilvántartás*.xlsx` (not bundled): `FlatRateTax` (átalányadó: revenue = paid net in the month paid, each payment in its own, cost ratio 45/80/90%, tax-free income half the yearly minimum wage, quarterly SZJA 15%, TB 18.5%, SZOCHO 13% with the minimum bases in main occupation, local tax bands, chamber fee, revenue limit, NAV tax codes and accounts, deadline the 12th after the quarter), `VatSummary` (by `VatReturnPeriod` of `Profile.vatPeriod`, by `Invoice.vatDate` as in the workbooks: an outgoing invoice on its payment date if paid within 45 days of the fulfillment, otherwise on the fulfillment + 45 days, an incoming one on its fulfillment date; rounded to thousands, deductible only if VAT registered, reverse charge self-assessed at 27%), `kataRevenue` (KATA: only the invoices and the 18 million limit; payments of the year), `vatCarriedIn` (a negative VAT balance carried to the next periods of the year).
- **Payments** (kiegyenlítések, since schema 16; before one paid date and amount per invoice, moved into one payment each): an invoice can be paid in parts: `Invoice.payments` (`InvoicePayment`, table `invoice_payments`: day, amount in the invoice's currency, method (transfer / cash / card), note; deleted with the invoice). The paid amount is their sum, `paidDate` the last one's day, `isPaid` when they add up to the gross amount (no "paid" switch). `getInvoices` loads them with the invoices; `FinanceDatasource.saveInvoice` saves them with the invoice in one transaction (a saved one updated, keeping its id; a new one inserted; the others deleted; the booked entries replaced), so a payment is saved through its invoice: `FinanceNotifier.savePayment` / `deletePayment`; `checkPayments` refuses more than the invoice (a credit note's are negative) or a 0. The invoice page lists them (`_Payments`: each opens `showPaymentDialog`, `widgets/payment_dialog.dart`, amount at most what is open; paid / open shown); a new invoice from the revenue record has one of the whole amount (`PaidInvoice`, whatever the gross becomes) until edited.
- **The revenue record's sorszám** (since schema 17): required, stored: `InvoicePayment.recordNumber` (not the row's id): the payments of a user's outgoing invoices numbered 1, 2, ... in each year, in date order (`FinanceDatasource.revenueOrder`: the day received, the invoice's fulfillment and number, then as recorded; one SQL window function). Not a strict numbering like the invoices': payments can be recorded in any order (e.g. bank by bank, a late one afterwards), only the end result must be right, so after every change of a user's invoices or payments (`saveInvoice`, `deleteInvoice`) `FinanceDatasource.renumber` numbers them again in the same transaction (an incoming invoice's has none). The changes aren't logged. `RevenueRecord` shows the stored numbers (its own count only for unsaved ones).
- **Invoices only users** (`Profile.invoicesOnly`: a flat-rate, VAT exempt sole proprietor; `pages/invoices_only_pages.dart`): no accounts, entries or balances (one who wants them makes a personal user). Their menu: dashboard (`_InvoicesOnlyDashboard`: this year's revenue with the limit, the next tax payment (last year's Q4 until its January deadline, then this quarter's so far), the open invoices, this year's latest invoices; no period picker; + makes an invoice), outgoing invoices (`InvoicesPage`; with EU reporting "Invoices", the incoming ones too: `Profile.incomingInvoices`, for the reverse charge VAT of EU services), revenue record (`RevenueRecordPage`, `RevenueRecord` in `providers/business/revenue_record.dart`: the revenues received, a line for each payment of an outgoing invoice, in the order received, numbered, by month, with the running total, the payment's net in forints at the invoice's rate, the same as `FlatRateTax` counts; "New revenue" (`addRevenue`): what came in on the bank account or in the till, a payment of an open invoice chosen in a sheet, or a new invoice paid the whole; a line opens its payment (`_editRevenue`): the day, amount, method and note, deleting it, or another invoice if it was chosen wrong (another partner's too; `showPaymentDialog(invoices:)`, `showInvoiceChoice`): it moves there as it is, keeping its id, both invoices saved in one transaction (`FinanceNotifier.savePayment(from:)`, `FinanceDatasource.saveInvoices`: the one it goes to first), at most that one's open amount; the invoices themselves are put right in the invoices), flat-rate tax (`FlatRateTaxPage`: the `FlatRateTaxView` of the year, `?quarter=` its first quarter (the dashboard's next tax payment opens its quarter of its year, `FlatRateTaxPage.location`); with EU reporting the VAT on a tab beside it), settings. Each page has the year in its app bar (`YearBar`, `businessYearProvider`, shared with the business page; the dashboard's buttons set this year). Their invoice form has no booking (account, category) and no direction without EU reporting; `FinanceNotifier.saveInvoice` doesn't book theirs (and clears the booking, so the entries of an invoice booked before go). `FinanceContent` doesn't ask them for an account. The business page's tabs (`InvoicesTab`, `FlatRateTaxView`, `VatTab`) are in `pages/business_tabs.dart` for both. `FlatRateTaxView` (an invoices only user's page and the other flat-rate users' business tab alike): a quarter or the year's summary chosen in a dropdown at the top, beside it the button to send or save what is shown (`SendReportButton`, `widgets/send_report_button.dart`); the current quarter first, the summary for a past year; the calculation one amount under the other: revenue − costs (`FlatRateQuarter.cost`, the cost ratio) = income − tax-free part (what is left of the year's half minimum wage) = tax base (the same in the summary and the exports; the tax-free revenue threshold only a note under the revenue limit, not a row: it read as a result); a quarter (`FlatRateQuarterView`): that calculation, its taxes and deadline, what to transfer, the year up to its end (the revenue against the limit, the taxes so far); the summary (`FlatRateSummaryView`): the revenue against the limit and the year's calculation, the year's taxes by kind, each quarter's total with its deadline (tapping one opens it); an invoice in a list is `InvoiceTile`, a row of a record `RecordTile` (`widgets/invoice_tile.dart`: the partner and the amount, below them the number and the details across the whole width, so it fits on a phone). The other sole proprietors keep the accounts and the business page as before.
- **Paid invoices are entries** (since schema 9; not an invoices only user's): an invoice with payments gets the account it was paid to (`paidAccountId`; one of its currency or HUF), a category (business income / expense, or for itemized taxation one with a `TaxTreatment`) and for a foreign currency the rate of the payment day (`paidExchangeRate`, the invoice's rate if not given). `invoiceEntries` (`data/invoice_booking.dart`) makes the entries of each payment, on its day (`Entry.invoiceId`); with a taxed category the VAT part goes to the VAT category (incoming) or the non-taxable income one (outgoing), in proportion when partly paid. `FinanceDatasource.saveInvoice` saves the invoice and replaces its entries in one transaction, deleting the invoice deletes them (cascade). So the balances, the dashboard, the statistics and the itemized ledger see the payments; the tax calculations still read the invoices. Such an entry opens its invoice (`openEntry` in `widgets/entry_tile.dart`). Unpaid invoices have no entry.
- **Itemized taxation** (vállalkozói SZJA, `TaxRegime.itemized`; tabs "Vállalkozói SZJA" and "Eszközök" in `pages/business_itemized.dart`), after `assets/vállalkozói szja 2026.xlsx` (EV = cash-flow ledger, ÉCS, HIPA): the ledger is the entries of the accounts (foreign currency entries have an `Entry.exchangeRate`, needed when the category is taxed); its columns are the `TaxTreatment` of the categories (the built-in `itemized` set can be added on demand, `FinanceRepository.addBusinessCategories`; own categories can get a treatment in the category dialog; an entry of the other type is a refund). `ItemizedTax`: per quarter revenue - costs (+ the loss of the quarter before) = base, VSZJA 9%, dividend base (osztalékalap) with 15% SZJA, advance due the 12th after the quarter; for the year the SZOCHO on the dividend base up to 24 minimum wages × 13% minus the SZOCHO paid, local business tax (revenue - material) × 2%. `Asset` (table `assets`) with `quarterlyDepreciation`: the yearly rate by calendar day from the purchase (the workbook counts one day more in every later quarter), 100% = written off at once. `test/itemized_tax_test.dart` checks the result against the workbook's own numbers (`test/fixtures/szja_2026_ev.json`, made from its EV sheet). Yearly legal amounts are in `TaxYear.known` (2025, 2026): add each new year there. Deadlines skip weekends only, not public holidays.
- **Currencies and exchange rates** (since schema 10): `Currency` has the forint and the ~30 currencies both the MNB and the ECB publish. Every user has a main currency (`Profile.mainCurrency`; HUF for a sole proprietor, a personal user chooses it once, when the user is made) and a rate source (`Profile.rateSource`: MNB, ECB, or manual only). A sole proprietor's is the rate of their own credit institution, typed in on the invoice (the law's default; "Own bank" in place of "Manual"), unless they chose the MNB's or the ECB's and reported it to NAV (`Profile.rateSourceReported`, since schema 16, the checkbox in `RatesPage`; a new choice must be reported again): `Profile.rateSourceInUse`, used everywhere (`FinanceState.rateSource`, the downloads). The choice is for a whole year. `ExchangeRate` (table `exchange_rates`, shared by the users): one unit of `currency` is worth `rate` of `base` on `date`; the MNB's in HUF, the ECB's stored as the value of a unit in EUR, manual ones in the base typed in. Rates are doubles (they aren't amounts). `RateBook` (`providers/finance/rate_book.dart`) finds a rate: the last one on or before the day (the first one before them), through the source's pivot for any two currencies, a manual one (either way round) before a downloaded one of its day or older, the other source if the chosen one has none. For the taxes `RateBook.official`: of the source alone, the last one published on or before the day, none if the downloaded ones end more than a week before it. An invoice in another currency gets it for its `rateDate` from the MNB / ECB if reported (shown, not typed in: `_OfficialRate` in `invoice_page.dart`; a missing one is downloaded by itself once, `RatesNotifier.downloadYear`, then with a button), otherwise the own bank's rate is typed in. `FinanceState.toMain` / `entryInMain` (an entry at its own `rate`) / `totalInMain` / `hasRate` convert. `RateDownloader` (`data/rates/rate_download.dart`): the MNB's SOAP service (http only: its WSDL says so; Android allows cleartext for www.mnb.hu alone in `res/xml/network_security_config.xml`) and the ECB's data API (CSV), with dart:io; only dates and currency codes are sent. `RatesNotifier.update` (`providers/rates_provider.dart`) downloads for the sources the users use the currencies they use, from January 1 of the year of the first entry / invoice (a user starting in the year finds the year's rates: the choice is for a whole year), what isn't there yet (after the last one, and from that January 1 if a currency's start later), then reloads; `main.dart` starts it unawaited at every start unless the switch in Settings → Data is off (`ratesAtStartProvider`). `RatesPage` (Settings → Data → Exchange rates; also from `MissingRatesNote`): main currency (shown only), source, download now, today's rate of the user's other currencies, the manual rates (`ManualRateDialog`).
- **An entry's rate** (since schema 12): an entry on an account of another currency than the user's main one stores its rate (`Entry.rate`, a double: main currency per unit; `Entry.exchangeRate` is it as HUF times the scale for the business taxes) and its source (`Entry.rateSource`: MNB / ECB, or manual). The entry form offers the day's rate (`FinanceState.offeredRate`: the day's last typed in, otherwise the downloaded one, with the source and day under the field); typing one in marks it manual (back to the downloaded one with the button; without rates a button downloads them), and saving makes it the day's rate (a manual `ExchangeRate`: one a day, the last one). `entryInMain` counts an entry at its own rate (the day's rate if it has none). After every download the personal users' entries without a rate get their day's downloaded one (`_fillEntryRates`; not an invoice's payment, a sole proprietor's or a manual-source user's). The main currency is chosen once, when a user is made.
- **Transfers** (átvezetés, since schema 13): money between two of the user's accounts, stored as two entries (`Entry.transferId`, table `transfers`: id and user; deleting it deletes both): an expense on the account it goes from, an income on the one it goes to. `transferSides` (`data/transfer_sides.dart`) makes them worth the same in the main currency: the rate of a side of another currency is made from the two amounts (a currency exchange: 390 000 Ft for 1000 EUR is 390), between two other currencies from the day's (or a typed in) rate of the one it goes from; a rate made so is also the day's manual rate. A transfer is no income or expense (`periodTotals`, `Statistics`, the type and "without category" filters leave it out), only in the balances, so an exchange changes no total, only the rates changing later do (revaluation). In the lists each side shows "To / From the other account" (`EntryTile.transferPeer`, `FinanceState.transferPeer`); either opens `TransferPage` (to look at first, then edit or delete it as one; `openEntry`); a new entry's type choice has "Transfer", which replaces the entry page with it.
- **Revaluation** (átértékelési különbözet): balances count at the last rate of their day, entries at their own rate; `FinanceState.periodChange` splits the change of the balance in a period (opening at the day before, closing at its last day) into the result (income - expenses), the opening entries and the revaluation (the rest). The dashboard's period card and the statistics' balance tab show the parts that aren't 0 (the summary tab doesn't). Income - expenses is "Különbség" (difference) in Hungarian, not "Eredmény".
- **Export** (`lib/export/`): a record to send is a `Report` (title, header lines (`profileHeader`: whose, when made), its tables (`ReportTable`: an optional title, typed columns: text / date / integer / decimal, rows: lines, subtotals, the total), footer lines, landscape or portrait), made into a PDF (`reportPdf`, the `pdf` package: A4, each table under its title, its head on every page, the bundled Roboto of `assets/fonts/` (Apache 2.0, from the Flutter SDK) for ő and ű, which the PDF's own fonts lack) or an XLSX (`reportXlsx`: written by hand, the format's XML zipped with `archive`, since the `excel` package conflicts with the app's packages; one sheet, the tables one after the other, real dates and numbers with formats, a single table's head frozen). `sendReport` sends it with the share sheet (`share_plus`: Android, Windows; it can't send a file on Linux: `canShareFiles`) or saves it (`file_picker`). So far the revenue record (`revenueRecordReport`, the ⇪ button of `RevenueRecordPage`, the year shown): sorszám, document number, day received, partner, description, payment method, in another currency its amount and rate (columns only if there is one), revenue in forints, running total, the month of the return (the month received, as the workbook's); the year's total, no months' (the app shows them); the revenue limit. The flat-rate tax (the ⇪ button of `FlatRateTaxView`, what it shows): a quarter (`flatRateQuarterReport`, portrait: the calculation with the bases, what to transfer with the tax codes and accounts, the deadline) or the year's summary (`flatRateSummaryReport`: a column a quarter and the year, the deadlines, the revenue limit and the tax-free revenue). New records are a `Report` builder each; the pages send them with `SendReportButton`.
- **Backup** (Settings → Data): `FinanceDatasource.backup` copies the whole database (every user) with `VACUUM INTO`; file_picker saves it. `restore` checks the file (a Fineva database, not of a newer schema), keeps the replaced database as `fineva.db.previous`, and opens (upgrades) the restored one.
- **Tax identifiers** (`utils/tax_ids.dart`): `parseTaxId` / `parseTaxNumber` / `parseEuVatNumber` check the check digits and return the stored form (10 digits; `12345678-1-12`; `HU12345678`) or null. `TaxNumberField` / `TaxNumberInputFormatter` (`widgets/tax_number_field.dart`) put the dashes in while typing. The name is required, the address and tax identification number are optional but must be valid when given. A sole proprietor must have a valid Hungarian tax number: `UserTypeChoice` asks it right under the choice and its form doesn't validate without it; `Profile.isComplete` is false without it (old data), and then SplashPage opens the onboarding, Skip is hidden and the business page asks to complete the profile. With EU reporting the EU VAT number is required and must be HU + the tax number's base number (`taxNumberBase`); switching EU reporting on fills it in from the tax number.
- **Logo:** the source is `assets/logo/*.svg` (`logo.svg` the icon, `mark.svg` the white "F." alone, `background.svg` the adaptive icon background). `tool/render_logo.sh` renders the PNGs (ImageMagick with librsvg) and runs flutter_launcher_icons and flutter_native_splash:create; their settings are in pubspec.yaml. Never edit the generated icons in android/ and windows/ by hand. The splash color `#167868` is `splashColor` (= `seedColor`) in constants.dart and in pubspec.yaml.

## Rules

- **Money:** amounts are `int`s in the smallest unit of the account's currency (`Currency.decimals`: HUF 0, EUR/USD 2), never doubles. `Currency.parse` / `format` / `toInput` convert. Amounts of different currencies are never added up as they are: they are converted into the user's main currency first (`FinanceState.toMain` and the rest), and what has no rate is left out and noted. An account's currency can't change once saved, because its entries are stored in that unit.
- **Entries:** `amount` is always positive (CHECK in the schema); `type` (income / expense) gives the sign (`signedAmount`). Dates are stored as `yyyy-MM-dd` text.
- **Opening balance = opening entry** (since schema 11): `Entry.opening`, no category, a negative one (overdrawn) as expense; the oldest of its day (`getEntries` orders `date DESC, opening ASC, id DESC`). It counts in the balances (a balance is the sum of the entries; `accounts.initial_balance` is a leftover, always 0, not in `Account`), never in the income / expenses (`FinanceState.periodTotals`, `Statistics`), nor as "without category" in the filter. A new account's dialog asks the opening balance and day and makes the entry (`FinanceNotifier.saveAccount(opening:)`); later it is edited or deleted like any entry (`EntryPage` with `opening`: a signed amount, no type or category). The upgrade turned each old opening balance into one on the account's first entry's day (today without entries).
- **A user's data is theirs only:** every user has their own categories, accounts (and so entries), invoices, assets and transfers. Writes are scoped to the current user at two levels: `FinanceNotifier` passes the current user's id with every save and delete, and `FinanceDatasource` only changes or deletes a row of that user (`update` / `delete` with `userId`: `WHERE id = ? AND user_id = ?`; an entry through its account, `saveEntry` / `deleteEntry`, and it can only go on the user's account in the user's category; an invoice and a transfer the same), throwing a StateError otherwise (the write returns false). Keep every new write scoped this way.
- **Built-in categories** come from `assets/categories.json` (since schema 15; `BuiltInCategories`, `data/built_in_categories.dart`, loaded in main.dart before the app starts, in the tests by `test/flutter_test_config.dart`, in the seeder by itself), so adding or removing one needs no code change. Each has a `key` (its `systemKey`), a `set` (`personal` / `business`: a new user's of their kind; `itemized`: on demand), type, color (one of `categoryColors`), icon (a key of `categoryIcons`), an optional `treatment` and its names (`en` required, `hu`); the names are there, not in the ARB files (`L10nNames.categoryName`; the stored name is the English one, shown if the key is unknown). At every opening of the database each user gets the ones of their sets they have never had, once (`given_categories`: the keys given to each user; `FinanceDatasource._giveNewBuiltIns`, `BuiltInCategories.missing`; the itemized set only if they have had one of it), so one they deleted doesn't come back. Never change or reuse a key; to remove one, mark it `"retired": true` (not given any more, its names still used), never delete it (`test/built_in_categories_test.dart` checks the file: complete entries, every key given once still there, the keys the code uses: `businessIncome`, `businessExpense`). A broken file stops the app at start. Renaming a category clears its key. A category's type can't change once saved.
- **Category scope and icon** (since schema 8): a category is personal or business (`CategoryScope`); a new user gets only their own kind, and only the current user's kind is shown (`FinanceState.visibleCategories`; users made before schema 9 may have both kinds, and an entry of the other kind keeps its category). The icon is a key of `categoryIcons` (`utils/category_icons.dart`), shown by `CategoryAvatar`; without one an icon is picked by the id.
- **Enums** are stored by `name` in the database: renaming an enum value needs a schema upgrade.
- **Localization:** edit `lib/l10n/app_en.arb` (the template) and `app_hu.arb`; the `app_localizations*.dart` files are generated. Access strings with `context.l10n`. The built-in categories' names are in `assets/categories.json`, not here.
- `EntryCategory` is not called `Category`, because Flutter's foundation library (exported by material.dart) has a class with that name.
